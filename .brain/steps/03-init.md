# Step 3: `init`

<!-- BEGIN:dotbrain status -->
Status: `done` · Assignee: user:dkowcun
<!-- END:dotbrain status -->

The last part of the MVP ([roadmap.md](../roadmap.md)). It builds on the starter template ([templates/README.md](../../templates/README.md), [setup.md](../architecture/setup.md)) and on the ready `lint` and `index` ([tooling-and-distribution.md](../architecture/tooling-and-distribution.md)). The role of `init` is set by a [decision](../decisions/tooling/2026-11-03-init-skeleton-for-agent.md).

## Goal

One command in an existing code repository and one agent session give a brain with content that follows from the code, not from empty templates. The wizard guides a person question by question, and the brain passes `lint` and `index --check` right after `init` and after the agent's session. The tool does what is deterministic, and the agent what requires judgment; a brain can still be set up without the tool, according to the procedure of the template ([decision](../decisions/tooling/2026-10-28-tools-optional.md)).

## Scope

- **The `init` wizard:** the questions of the procedure of the [starter template](../../templates/README.md) asked one at a time, in its order: name of the brain, language, owner, description of the project, languages of code, comments, commits, branch names and PRs, order of work, steps named by the keys of tickets. For each question a default value, when it can be determined (the name of the directory, the git configuration, the default rule of the order of work, steps with numbers), a check of the answer (e.g. a name in kebab-case, a BCP 47 tag) and a summary before writing.
- **Steps named by the keys of tickets:** a new question of the template's procedure, whether the steps of the brain have the keys of tickets from the tracker in their file names instead of numbers ([decision](../decisions/model/2026-11-05-step-ids-from-tracker.md)). With the answer "yes", a decision with `apply: always` is written in `decisions/process/` from the new template `templates/step-ids.md`, after the model of `templates/order-of-work.md`.
- **Answers without questions** from options or an answers file, for scripts and tests, with the same result as the wizard.
- **The skeleton** from the answers: `.brain/README.md` with the manifest, the decisions from the answers (languages, order of work, optionally ticket keys) in `decisions/process/`, the decision list, the index block, the managed blocks in `CLAUDE.md`, `AGENTS.md` and `.github/copilot-instructions.md`, the `brain-review` subagent. The content comes from files in `templates/` read at runtime, and the views are generated by the same logic as `index`.
- **The setup instruction for the agent** in a separate file in the root directory of the repository (`DOTBRAIN-SETUP.md`), outside `.brain/`, and one line pointing to it in `CLAUDE.md`, `AGENTS.md` and `.github/copilot-instructions.md` outside the managed block, so that the agent finds the instruction also without the instruction `init` prints at the end. The file is self-contained: `init` pastes into it the remaining steps of the procedure (translation, code scan, architecture, decisions from the code, check) and the templates needed (area, `proposed` decision), so it works without access to the dotbrain repository (another person, a cloud session, a tool without access outside the repository). At the end the agent deletes the file and the lines pointing to it. The managed block stays deterministic, and the specification unchanged; a temporary part of the block would require a new field in the manifest with the state of the setup.
- **The template's procedure with a code scan:** the agent translates the skeleton for a brain in another language, describes the architecture based on the code, with links to files, and records decisions read from the code as `proposed` with their source ([pattern](../decisions/agents/2026-10-28-decisions-extracted-from-conversations.md)); the code stays at its source, and what follows from it goes into the brain ([decision](../decisions/model/2026-10-28-brain-is-not-a-data-lake.md)). This is the same procedure the agent follows without the tool; then it asks the wizard's questions itself.
- **Existing instruction files:** the block goes after the first heading, the rest of the file stays unchanged.
- **Checks during the setup:** git does not ignore `.claude/rules/` and `.claude/agents/` ([decision](../decisions/agents/2026-11-03-claude-code-rules-directory.md)); `init` refuses when the repository already has `.brain/README.md`, and overwrites nothing.
- The command in the repository's `README.md`, tests in `tools/test/`.

## Out of scope

- The address of the tracker in the manifest for links to tickets: requires a change of the specification, a separate decision ([decision on keys](../decisions/model/2026-11-05-step-ids-from-tracker.md), Consequences).
- Keys for steps without a ticket (e.g. a change without a task) with a prefix set by the maintainers of the repository: the format of a step already allows them (a letter, letters or digits, a hyphen and a number), so a brain that wants them adds this to its decision on keys; the wizard does not ask about it.
- Plugins and skills for AI tools and an MCP server: the distribution channels are an [open decision](../decisions/tooling/2026-10-28-distribution-channels.md).
- Publishing the package: `init` runs from the dotbrain repository, like `lint` and `index`.
- Translation by the tool itself.
- A live trial in GitHub Copilot: in the MVP we check only Claude Code live; `init` writes `AGENTS.md` and `.github/copilot-instructions.md` with the same block, but without a trial with the tool.

## Acceptance criteria

1. The wizard asks the questions of the template's procedure one at a time, in its order, including the question about steps named by the keys of tickets, with default values, rejects invalid answers giving the reason and shows a summary before writing. The same answers given without questions give a result identical to the character.
2. After `init` in a repository without a brain, both empty and with existing code, `lint` reports no errors, and the check mode of `index` finds no stale views; the same with the answer "yes" to the question about ticket keys, when the brain has a decision on them with `apply: always`, and the rule is in the managed blocks. In a repository with a brain, `init` ends with an error and changes no file.
3. In a repository with an existing `CLAUDE.md` with a heading and content, the block goes after the first heading, and the rest of the file is unchanged.
4. A change of the text of a template in `templates/` changes the output of `init` without a change of the code.
5. A new Claude Code session in a real code repository outside dotbrain, after the instruction printed by `init`, writes an architecture matching the code and with links to it, records decisions read from the code as `proposed` with their source, deletes the setup instruction file and the lines pointing to it, and leaves a brain on which `lint` and the check mode of `index` pass. Checked for a brain in English and in Polish.
6. The repository's checks pass; the tool works offline on Node 24 or newer, without runtime dependencies.

## Stages

1. The `init` wizard with the skeleton and the setup instruction, with the question about ticket keys and the `templates/step-ids.md` template, in an empty repository and in a repository with code (criteria 1–4 and 6).
2. The agent takes over after `init`: the template's procedure with a code scan and live trials in Claude Code (criterion 5).
