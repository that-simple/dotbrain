# Step 7: a lighter entry

<!-- BEGIN:dotbrain status -->
Status: `done` · Assignee: user:dkowcun
<!-- END:dotbrain status -->

The review of the framework on 2026-11-17 found the overengineering named first in [risks.md](../risks.md) already showing in three places. The managed block in `CLAUDE.md` has about 1300 words and is in the agent's context in every task, although most of it is the mechanics of work on the brain (writing decisions and steps, regenerating views, conflicts, logs, numbering), needed only when the agent works on the brain. The 21 rules of the contract are written twice in prose, in [spec/agent-contract.md](../../spec/agent-contract.md) and in [agent-contract.md](../architecture/agent-contract.md). And the framework promises that a person can keep the generated views by hand, which in practice nobody does, and which makes the specification read as if a person were its compiler.

In the discussion of the review, the owner set who reads what (conversation with the agent, 2026-11-17): dotbrain is a framework for an agent with a person in the loop. A person reads and agrees steps, and looks at a step again when it is carried out; reads the content of decisions; and possibly the risks. For anything else, the person asks the agent about the project, and the agent finds the answer in the brain.

## Goal

The agent gets the core of the contract in every task and the rules of work on the brain only when it works on the brain, without following a link and without a network. The contract has one normative text, in the specification, and the brain explains it without restating it. The framework names the `dotbrain` CLI as the way to keep generated views and instruction files, and an agent following the specification as the way without it; no document tells a person to keep the views by hand. The framework says how the brain is used: a person reads steps, the content of decisions and risks, and for the rest asks the agent, which answers from the brain.

## Scope

- **One source of the contract.** [agent-contract.md](../architecture/agent-contract.md) no longer restates the rules of the contract: it keeps the structure of the contract (the core, the work on the brain, the delivery), the reasoning and the links to the decisions, and points to [spec/agent-contract.md](../../spec/agent-contract.md) for the normative text. Other documents of this brain that restate rules of the contract link to it instead.
- **The core in the block, the rest for the brain directory.** The compact form in `spec/adapters/agents.md` is split into two parts:
  - **Core**, in the managed block of every root instruction file: the brain binds, start with the index, a decision before the work, do not resolve `proposed` decisions, a decision from a conversation is `proposed`, report discrepancies, plan before work (a new step is only written as `draft`, a person sets `agreed`, keep to the scope of a step), talk to people in their language, the brain binds the code, the languages of the work and the order of work are decisions, checks before a stage and before `done`, the review before `done`, before merging into the main branch and before committing to it.
  - **Work on the brain**, in a rule file applied to `<brain-path>/**`: the file, frontmatter and sections of a new decision, detecting parallel decisions, regenerating generated views, conflicts (generated views, documents, contradicting decisions, logs, step numbers), `in-progress`, `assignee`, stages and the log of a step, raw material, what the brain does not keep, writing to the brain in its language.
  - A table in `spec/adapters/agents.md` assigns every rule of `spec/agent-contract.md` to exactly one part.
  - The rule file per tool, generated only when the root instruction file of the tool exists: `.claude/rules/<brain>.md` with `paths: ["<brain-path>/**"]` for `CLAUDE.md`, `.github/instructions/<brain>.instructions.md` with `applyTo: "<brain-path>/**"` for `.github/copilot-instructions.md`, and a nested `<brain-path>/AGENTS.md` for `AGENTS.md`, linked from a line in "Rules for specific files" of its block. The name `<brain>` without a suffix does not collide with the rule files of documents, `<brain>-<name>`. The core rule "start with the index" makes the agent read a file in the brain before it writes to it, so the rule file is in its context by then.
  - The specification: the statement in `spec/README.md` that the managed block holds everything needed for everyday work covers the block and the rule file; `V-VIEWS` in `spec/validity.md` covers the new files; the conformance cases are rebuilt.
  - The tools: `tools/src/contract.ts` reads both parts, `tools/src/views.ts` generates the rule files and removes stale ones, `init` and the starter template (`templates/README.md`, `templates/managed-block.md` and a template of the rule file) create them; tests.
  - This repository: the block in `CLAUDE.md` regenerated and `.claude/rules/dotbrain.md` added; [ai-integrations.md](../architecture/ai-integrations.md) and [agent-contract.md](../architecture/agent-contract.md) describe the split.
  - A decision in `decisions/agents/` on the split, written in the work on the step as `accepted`, because it carries out this step; if in the work it were to bring anything beyond this scope, it is written as `proposed`.
- **The CLI as the recommended path.** A decision in `decisions/tooling/` supersedes [optional tools](../decisions/tooling/2026-10-28-tools-optional.md): generated views and instruction files are kept by the `dotbrain` CLI, and without it by an agent following the specification; a person keeping them by hand is not a supported way of working; people still read and write documents by hand; no feature of the framework requires the CLI. It is written in the work on the step as `accepted`, on the same terms as the decision above. The wording follows it in `README.md`, `spec/README.md`, [overview.md](../architecture/overview.md) (principles 4 and 5), [tooling-and-distribution.md](../architecture/tooling-and-distribution.md) and the generated views of the starter procedure in `templates/README.md`.
- **An agent with a person in the loop.** A decision in `decisions/model/`, written in the work on the step as `accepted` on the same terms as the decisions above: dotbrain is run through an agent with a person in the loop; a person reads and agrees steps and looks at a step again when it is carried out, reads the content of decisions and possibly the risks; for anything else, the person asks the agent, which finds the answer in the brain. The decision describes how the brain is used; it sets no new requirements for documents and changes none of the existing ones.

  It goes into the principles in [overview.md](../architecture/overview.md) and into `README.md` (how a person works with a brain). The contract gets a core rule: asked about the project, the agent answers from the brain, links the documents the answer rests on, and says when the brain does not cover the question. The rule goes into `spec/agent-contract.md`, the core part of the compact form (within the limit of criterion 2), the conformance cases and the block in `CLAUDE.md` of this repository.

## Out of scope

- The overlap of [core-model.md](../architecture/core-model.md) with `spec/documents.md` and other restatements of the specification outside the contract: a matter for a separate step or decision.
- A word budget for the core of the contract checked by `lint`. The core is fixed text from the specification, the same in every brain: a brain cannot change it, and a block changed by hand is already a `V-VIEWS` violation. The core grows only with a change of the specification, so the limit of acceptance criterion 2 is checked by a test in this repository, before a release.
- A live trial with a second AI tool ([decision](../decisions/agents/2026-11-17-mvp-gate-without-second-ai-tool.md)) and changes to [step 6](06-lint-hook.md).
- Instruction files of other tools, such as Cursor rules.
- A migration: the change is made in specification 0.1, before its publication.

## Acceptance criteria

1. [agent-contract.md](../architecture/agent-contract.md) has no list of the rules of the contract and links to `spec/agent-contract.md` for them; no other document of this brain restates a rule of the contract.
2. The core part of the compact form has at most 400 words, counted as in the budget of `always` rules, and a test in `tools/test/` checks it; the table in `spec/adapters/agents.md` assigns every rule of `spec/agent-contract.md` to exactly one part.
3. `index` creates and updates the rule file of the brain for each root instruction file that exists, as listed in the scope, and removes a stale one; `lint` and `index --check` report a missing or stale rule file as `V-VIEWS`; the conformance cases cover the three tools.
4. A repository set up by `init` or by the starter procedure has the rule file next to every instruction file it creates.
5. The decision on the split is in `decisions/agents/`, the decision on the CLI is in `decisions/tooling/`, [optional tools](../decisions/tooling/2026-10-28-tools-optional.md) has `status: superseded` and `superseded-by`, and the decision list is regenerated.
6. None of `README.md`, `spec/README.md`, `templates/README.md`, [overview.md](../architecture/overview.md) and [tooling-and-distribution.md](../architecture/tooling-and-distribution.md) tells a person to keep generated views by hand.
7. The decision on an agent with a person in the loop is in `decisions/model/`; [overview.md](../architecture/overview.md) and `README.md` say that a person reads steps, the content of decisions and risks, and asks the agent for the rest; `spec/agent-contract.md` and the core part of the compact form have the rule on answering questions about the project from the brain, and the block in `CLAUDE.md` of this repository carries it.
8. The repository's checks pass after every stage.

## Stages

1. One source of the contract: [agent-contract.md](../architecture/agent-contract.md) and the other documents of this brain, without changes to the specification or the tools (criterion 1).
2. The core in the block and the rule file for the brain directory: the specification, the tools, the templates, the conformance cases, this repository and the decision on the split (criteria 2–4 and the part of 5 on the split).
3. An agent with a person in the loop: the decision superseding optional tools, the decision on who reads what, the contract rule on answering questions about the project, and the wording that follows them (the rest of criterion 5, criteria 6 and 7).
